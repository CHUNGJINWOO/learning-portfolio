# 학습 운영 가이드 (Learning System Guide)

본 문서는 `02_ros2_core_curriculum`을 장기적인 통합 학습 포트폴리오로 운영하기 위한 **학습 철학, 디렉터리 경계, 5단계 학습 상태 머신, 파일 투입 워크플로 및 AI 에이전트 작업 수칙**을 정의하는 공식 시스템 가이드라인입니다.

---

## 1. 레포의 목적과 핵심 운영 원칙

본 저장소는 단순한 코드 저장소나 필기 모음이 아닙니다.
1. **이해와 축적 중심**: 학교와 개인 학습에서 배운 내용을 자신의 언어로 재구성하여 체계적으로 축적합니다.
2. **First-Principles Thinking**: 코드가 동작하는 결과에 그치지 않고, *왜 이 방식을 선택했는지*, *어떤 대안이 존재하는지*, *잠재적 동시성 및 안전성 문제는 무엇인지*를 철저히 파악합니다.
3. **Clean-room 청정 구현**: 비공개 강의 자료나 상용 교재를 복제하지 않고, 공식 오픈소스 표준 문서에 기반해 자체 설계한 예제만을 다룹니다.
4. **엄격한 기술적 정직성**: 검증된 항목과 미검증된 항목을 명확히 구분합니다. 확인하지 않은 내용을 추정으로 통과 처리하지 않습니다.
5. **허위 학습 배제 원칙**: 아직 스스로 학습하고 이해하지 못한 주제를 미리 구현하여 포트폴리오를 채우지 않습니다.

## 2. 디렉터리별 역할과 경계

각 디렉터리는 명확한 책임과 경계를 가집니다.

```text
learning-portfolio/
├── inbox/       # [수집/대기] 전체 도메인 공통 신규 자료 임시 대기소 (단일 진입점)
├── docs/        # [운영 표준] 학습 워크플로우 및 템플릿 표준
└── 02_ros2_core_curriculum/
    ├── docs/       # [공식 문서] Phase별 공식 기술 가이드 및 도메인 운영 가이드
    ├── src/        # [공식 소스] 빌드·린트·런타임 검증을 통과한 실행 가능한 패키지
    ├── notes/      # [개념 노트] 배운 지식을 자신의 문장으로 재구성한 이론 및 분석 자료
    └── exercises/  # [복습/평가] 복습 질문, 자가점검 퀴즈, 미니 응용 실습 과제
```

### 2.1. `src/` (공식 패키지 공간)
- **역할**: ROS 2 빌드 시스템(`colcon`, `ament_python`) 또는 정규 빌드 파이프라인을 통과한 독립 실행 패키지.
- **품질 기준**: `ament_flake8`(99자 제한) 통과, 구문 에러 0건, 명확한 진입점(`console_scripts`) 및 설정 파일 포함.

### 2.2. `docs/` (공식 기술 가이드)
- **역할**: 패키지 구현의 배경, 수학적 수식, 아키텍처 다이어그램, 런타임 검증 결과, API 비교를 담은 종합 가이드.
- **성격**: Phase 1~5와 같이 완성도가 입증된 공식 릴리스 문서.

### 2.3. `notes/` (지식 재구성 노트)
- **역할**: 학교 수업, 개인 학습, 기술 문서에서 배운 핵심 원리를 **자신의 언어로 요약·정리**한 마크다운 문서.
- **경계**: 원본 강의 슬라이드(교수자 저작물)를 그대로 두지 않고, 핵심만 소화하여 작성.

### 2.4. `exercises/` (복습 및 자가점검)
- **역할**: 학습한 내용의 이해도를 측정하기 위한 복습 질문(Self-Reflection), 자가점검 퀴즈, 코드 변형 실습 과제.
- **경계**: 단순 정답 암기가 아니라, "왜 그런 동작이 발생하는가?"를 묻는 서술형/원리 중심 문항 구성.

### 2.5. 루트 `inbox/` (신규 자료 단일 대기소)
- **역할**: 새로 학습한 원시 자료(코드, 필기, 터미널 로그 등)가 들어와 분석을 기다리는 저장소 루트의 단일 임시 버퍼 (`/inbox`).
- **운영 기준**: 상세 워크플로우 및 처리 원칙은 저장소 공통 표준 문서인 [`docs/LEARNING_WORKFLOW.md`](../../docs/LEARNING_WORKFLOW.md)를 준용합니다.
- **경계**: 정식 사용자 승인 전에는 원본을 임의로 수정하거나 삭제하지 않습니다.

## 3. 5단계 학습 상태 관리 체계

지식의 '진짜 이해도'는 코드 빌드 성공 여부와 구분하여 **5단계 상태 머신**으로 관리합니다:

```text
[1. INGESTED] ──► [2. IN_PROGRESS] ──► [3. PRACTICED] ──► [4. NEEDS_REVIEW] ──► [5. VERIFIED_UNDERSTANDING]
  (자료 수집)         (학습 중)           (실습 확인)         (복습 필요)             (이해 확인)
```

| 상태 코드 | 상태 명칭 | 정의 및 진입 조건 | 전이 기준 |
| :--- | :--- | :--- | :--- |
| **`INGESTED`** | **자료 수집** | `inbox/`에 학습할 파일이 투입된 상태. | 자료 식별 완료 시 `IN_PROGRESS`로 전이 |
| **`IN_PROGRESS`** | **학습 중** | 개념 문서를 읽고 주석을 달며 이론과 코드를 분석하는 단계. | 최소 예제 작성 및 실행 시 `PRACTICED`로 전이 |
| **`PRACTICED`** | **실습 확인** | 코드를 직접 빌드하고 터미널에서 실행하여 정상 출력을 직접 확인한 상태. | 설명 미흡 또는 복습 필요 인지 시 `NEEDS_REVIEW`로 전이 |
| **`NEEDS_REVIEW`** | **복습 필요** | 코드는 동작하지만 원리를 남에게 설명하거나 예외를 다루기 모호한 상태. | 복습 문제 풀이 및 자가진단 수행 |
| **`VERIFIED_UNDERSTANDING`** | **이해 확인** | 아래 3대 조건을 모두 충족하여 스스로 설명하고 응용할 수 있는 상태. | 최종 학습 달성 (지속 보존) |

### ⚠️ [핵심 원칙] 실습 검증 상태와 학습 상태의 분리
- **빌드 성공 $\neq$ 이해 완료**: 코드가 정상 빌드되고 콘솔 로그가 나왔다고 해서 학습자가 원리를 이해한 것은 아닙니다. 이는 `PRACTICED`(실습 확인)일 뿐입니다.
- **이해 확인 부여 기준**:
  - ① 동작 원리와 설계 이유를 자신의 문장으로 명확히 설명할 수 있음.
  - ② 복습 문제(응용 퀴즈)를 외부 도움 없이 스스로 해결함.
  - ③ 관련 오류나 예외 상황 발생 시 스스로 원인을 찾아 디버깅할 수 있음.
- **AI 임의 부여 금지**: AI 에이전트는 사용자의 설명이나 복습 문제 풀이 증거 없이 임의로 `VERIFIED_UNDERSTANDING`을 부여할 수 없습니다.

## 4. 신규 자료 투입 및 통합 워크플로 (10단계 안전 절차)

사용자가 `inbox/`에 새로운 파일을 투입했을 때 처리하는 표준 절차입니다:

```text
[사용자 투입] ──► [1. 탐지 및 메타데이터 분석] ──► [2. 내용 및 주제 식별] ──► [3. 기존 자료 대조]
                                                                                      │
[사용자 승인] ◄── [6. 변경 제안서 제출] ◄── [5. 안전성 사전점검] ◄── [4. 통합 방식 결정]
      │
      ▼
[실제 반영 (notes / exercises / src)] ──► [inbox 정리]
```

1. **[투입]**: 사용자가 새 자료를 `inbox/` 디렉터리에 배치.
2. **[탐지 및 메타데이터 분석]**: 파일 목록, 형식, 용량, 최종 수정 시점 확인.
3. **[내용 및 주제 식별]**: 파일의 핵심 주제(Python, C, ROS 2, Embedded, Math 등) 파악.
4. **[기존 자료 대조]**: 기존 `docs/`, `notes/`, `src/`와의 연관성 및 중복 검토.
5. **[자료 성격 분리]**: 원시 메모, 실행 코드, 복습 문제 등으로 분류.
6. **[통합 계획 수립]**: 기존 문서 보완 여부, 신규 `notes/` 생성 여부, `exercises/` 추가 여부 결정.
7. **[코드 안전성 사전점검]**: 실행 가능한 코드의 경우 문법(`py_compile`) 및 스타일(`flake8`) 점검.
8. **[검증 상태 명시]**: 직접 실행 가능한지(VERIFIED), 환경 제약이 있는지(NOT_VERIFIED) 구분.
9. **[사전 변경 제안서 제출]**: 어떤 파일을 어디에 추가/수정할지, 왜 그렇게 하는지 사용자에게 보고.
10. **[사용자 명시적 승인 후 반영]**: **사용자의 승인이 떨어진 뒤에만 실제 반영을 수행**하며, `inbox/`의 원본은 안전하게 회수/정리.

## 5. 원본 보존, 저작권 및 보안 수칙

1. **학교 자료 원본 보존**:
   - 학교(`school/`)의 강의 슬라이드, 과제 원본 파일은 변경 없이 영구 보존합니다.
   - 포트폴리오로 일괄 복사하지 않으며, 학습자가 자신의 문장으로 재해석한 지식만 포트폴리오에 수용합니다.
2. **저작권 보호**:
   - 학교 교수자의 강의 슬라이드(PPTX, PDF) 원본이나 상용 출판물의 텍스트를 공개 저장소에 그대로 업로드하지 않습니다.
3. **비밀정보 및 개인정보 보호**:
   - API 키, 토큰, 비밀번호, 사설 서버 접속 정보, 개인 식별 정보는 절대 문서나 코드에 포함하지 않습니다.

## 6. AI 에이전트의 작업 수칙 (Agent Rules)

본 저장소에서 작업하는 모든 AI 에이전트는 다음 수칙을 엄격히 준수해야 합니다:

1. **선 조사 후 제안 (Read First)**: 작업을 시작하기 전에 관련 파일과 환경의 실제 상태를 직접 읽고 확인한다.
2. **중복 확인 (Check Redundancy)**: 새 문서를 만들기 전에 기존 자료와 겹치는 내용이 없는지 대조한다.
3. **변경 계획 사전 제시 (Propose Before Write)**: 변경 대상, 이유, 예상 영향을 사용자에게 먼저 보고한다.
4. **승인 범위 엄격 준수 (Scope Adherence)**: 사용자가 명시적으로 승인한 범위만 최소 수정하며, 임의로 추가 확장을 하지 않는다.
5. **투명한 결과 보고 (Honest Verification)**:
   - 직접 확인한 사실(`VERIFIED`)과 이전 보고서에 근거한 사실(`PREVIOUSLY_REPORTED`)을 구분한다.
   - 확인하지 못한 항목(예: 헤드리스 환경의 GUI)은 솔직하게 `NOT_VERIFIED`로 기록한다.

## 7. 문서 및 코드 예제의 품질 기준

1. **코드 품질**:
   - Python: PEP 8 준수, 줄 길이 99자 제한(`ament_flake8`), 타입 어노테이션 명시.
   - 방어적 예외 처리: 입력값 유효성 검사, 타이밍 레이스 컨디션 방어.
   - 외부 의존성 최소화: 표준 라이브러리 우선 사용 원칙.
2. **문서 품질 (표준 10대 블록 채택)**:
   - 모든 기술 문서는 가능하면 다음 흐름을 갖춥니다:
     `학습 목표` $\to$ `쉬운 개념 설명` $\to$ `동작 원리와 필요 이유` $\to$ `최소 실행 예제` $\to$ `실행 방법 및 기대 결과` $\to$ `오류 일지 및 해결 과정` $\to$ `핵심 요약` $\to$ `복습 질문` $\to$ `자가점검 응용 과제` $\to$ `미이해 항목 및 후속 과제`.
