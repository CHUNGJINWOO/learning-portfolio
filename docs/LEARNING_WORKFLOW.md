# 🧭 학습 자료 수집 및 관리 워크플로우 (Learning Workflow)

본 문서는 사용자가 새로 학습한 원시 자료를 `inbox/`에 투입했을 때, AI 에이전트와 함께 이를 검토·분류하고 기존 6대 도메인으로 안전하게 통합하는 **10단계 표준 운영 절차**를 정의합니다.

공통 개발 원칙 및 Agent 기본 행동 지침은 [Guidebook AI Agent Guide](https://github.com/CHUNGJINWOO/guidebook/blob/main/docs/ai/AI_AGENT_GUIDE.md)를 준용하며, 본 문서는 학습 포트폴리오의 구체적 지식 편입 절차에 집중합니다.

---

## 📌 핵심 원칙 (Core Principles)

1. **원본 불변 원칙 (Non-Destructive Principle)**:
   - 사용자의 명시적 승인 전까지 `inbox/`의 원본 파일은 임의로 수정, 이동, 삭제되지 않습니다.
2. **학습 성과의 진실성 보장**:
   - 실제로 학습하지 않은 기술을 학습 성과로 기록하지 않으며, 검증되지 않은 항목은 결코 `PASS` 또는 완료로 표기하지 않습니다.
3. **독립 3영역 상태 관리**:
   - 지식 이해(학습 기록), 실행 가능성(기술 검증), 제약 조건(확인 필요 사항)을 상호 독립적으로 구분하여 관리합니다.
4. **점진적·승인 기반 반영**:
   - AI 에이전트는 계획을 제안하고, 사용자의 검토 및 승인을 거쳐 반영합니다.
5. **AI 작성 문서와 학습 완료 분리**:
   - AI 에이전트가 작성한 문서나 요약본만으로 학습 완료를 인정하지 않으며, 학습자의 실제 학습 및 검증 근거가 확인된 항목만 학습 성과로 인정합니다.

---

## 🔀 2가지 워크플로우 유형 (Workflow Types)

학습 자료의 처리 상황에 따라 다음 두 가지 흐름을 명확히 구분하여 운영합니다:

### 유형 A — 신규 자료 투입 (New Ingestion Workflow)
- **대상**: 새로 학습하여 아직 포트폴리오에 정식 편입되지 않은 외부 실습 코드, 메모, 패키지.
- **경로**: 루트 `inbox/`에 단일 파일 또는 패키지 디렉터리 통째로 배치.
- **절차**: 아래의 [10단계 표준 처리 절차]를 온전히 적용하여 탐지 → 분석 → 중복 검토 → 제안 → 사용자 승인 → 적정 도메인 통합 순으로 진행.

### 유형 B — 기존 자료 정비 (In-Situ Maintenance Workflow)
- **대상**: 이미 6대 도메인(`01`~`06`)에 안정적으로 배치된 기존 학습 코드, 노트북, 기술 문서.
- **원칙**: 기존 자료 정비를 위해 불필요하게 `inbox/`로 복제하거나 이동하지 않고, **해당 도메인 제자리(In-Situ)에서 직접 분석 및 보강**.
- **절차**:
  1. 기존 파일의 설명 누락, 상호 참조 링크 단절, 검증 근거 미비 사항 조사.
  2. 필요한 설명 보완, 상호 참조 링크, 복습 질문(자가점검용) 최소 변경안 수립.
  3. **사용자의 사전 검토 및 명시적 승인** 획득.
  4. 승인된 범위에 한하여 제자리에서 정밀 수정 및 링크/무결성 검증.
- **공통 원칙**: 유형 A와 유형 B 모두 실제 파일 수정과 Git 반영 전에 **반드시 사용자의 명시적 승인**을 받습니다.

## ⚙️ 10단계 표준 처리 절차 (신규 자료 투입 기준)

```text
[1. 자료 투입]
      │
      ▼
[2. 읽기 전용 분석] ──► [3. 기존 도메인 조사] ──► [4. 중복 및 연관성 대조]
                                                               │
[7. 사용자 검토/승인] ◄── [6. 설명 및 복습 질문 제안] ◄── [5. 학습 vs 검증 분리]
      │
      ▼
[8. 도메인 안전 통합] ──► [9. 기술 검증 실시] ──► [10. 사용자 승인 후 커밋/푸시]
```

### 1단계: 사용자 자료 투입 (Input)
- 사용자가 새로 학습한 원시 코드, 실습 결과, 필기 메모, 트러블슈팅 로그를 루트 `inbox/` 디렉터리에 배치합니다.
- `inbox/`에 파일을 넣는 행위는 검토 대기 공간에 투입하는 것일 뿐, Git 커밋 승인을 의미하지 않습니다.
- 대용량 데이터, 토큰, 비밀번호, 학교 원본 교재 등 제외 대상이 포함되지 않도록 주의합니다.
- 외부 코드나 강의 자료의 경우 출처와 재배포 가능 여부(라이선스 및 저작권)를 확인합니다.

### 2단계: AI 읽기 전용 분석 (Read-Only Analysis)
- 에이전트는 파일의 확장자, 언어, 용량, 작성 시점, 주석, 코드 구조를 읽기 전용으로 파악합니다.
- 파일의 출처(공식 문서, 교재, 강의 실습, 자가 실험 등)를 식별합니다.

### 3단계: 기존 도메인 조사 (Domain Inspection)
- 투입된 자료가 6대 학습 도메인 중 어디에 해당하는지 식별합니다:
  - `01_python_and_oop`: Python 객체지향, 수치 신호 모델링
  - `02_ros2_core_curriculum`: ROS 2 통신 패러다임, 파라미터, TF2, 오케스트레이션
  - `03_robotics_algorithms`: 점유격자, 2D 레이 트레이싱, 좌표 기하
  - `04_computer_vision`: 영상처리, OpenCV 필터, 에지 검출, 행렬 연산
  - `05_embedded_systems`: 마이크로컨트롤러, 센서 인터페이스, Wokwi 시뮬레이션
  - `06_cloud_and_devops`: OCI, VPN, 보안, 원격 개발 환경

### 4단계: 내용 중복 및 관련성 비교 (Diff & Synergy Check)
- 기존 문서(`notes/`, `docs/`) 및 소스(`src/`, `exercises/`)와의 중복 여부를 대조합니다.
- 기존 지식의 '단순 중복'인지, '기존 지식의 심화·보완'인지, '완전한 신규 주제'인지 판별합니다.

### 5단계: 학습 내용과 기술 검증 근거 구분 (Separation of Concerns)
- 수집된 정보를 3개 독립 영역으로 분리합니다:
  - **학습 기록**: 개념 요약, 동작 원리, 학습자의 소화 내용
  - **기술 검증 근거**: 구문 검사, 빌드 로그, 터미널 실행 출력
  - **확인 필요 사항**: 미검증 항목, 환경 제약으로 확인하지 못한 사유

### 6단계: 이해를 돕는 설명 및 복습 자료 제안 (Proposal Drafting)
- 에이전트는 원시 자료를 포트폴리오 규격에 맞춘 마크다운 초안으로 구성합니다.
- [`docs/LEARNING_TEMPLATE.md`](LEARNING_TEMPLATE.md) 규격을 적용하여 작성합니다.
- 학습자의 자기점검을 도울 수 있는 복습 질문(Self-Reflection Questions)을 작성하여 제안합니다.
  *(주의: AI가 사용자의 이해도 검증 결과를 임의로 작성하지 않음)*

### 7단계: 사용자 제안 내용 검토 (User Review & Alignment)
- 에이전트는 변경 계획서(배치 대상 경로, 신규 파일, 수정 파일, 보존 계획)를 사용자에게 보고합니다.
- 사용자는 제안된 설명의 정확성과 분류의 적절성을 검토하고 승인 여부를 결정합니다.

### 8단계: 승인된 자료만 해당 도메인으로 통합 (Safe Integration)
- 사용자의 명시적 승인이 떨어진 자료에 한하여 지정된 도메인 디렉터리로 통합합니다. 사용자 승인 전에는 자동 삭제, 이동, 수정을 절대 수행하지 않습니다.
- 미승인 자료나 보류된 파일은 `inbox/`에 안전하게 남겨둡니다.

### 9단계: 문법·빌드·실행 등 가능한 검증 실시 (Verification Execution)
- 통합된 파일의 무결성을 검증합니다:
  - Python 코드: `python3 -m py_compile`, 스타일 점검
  - ROS 2 패키지: `colcon build --symlink-install --packages-select <pkg>`
  - Markdown 문서: 내부 상대 링크 및 `git diff --check`
- 검증 결과는 문서 내 기술 검증 영역에 명확한 근거와 함께 기록합니다.

### 10단계: 사용자 별도 승인 후 Git 커밋 및 푸시 (Final Commit & Push)
- 모든 검증이 완료된 후, 변경 내역과 diff를 요약하여 사용자에게 보고합니다.
- 실제 커밋 시에는 사용자가 최종 승인한 파일만 명시적으로 스테이징(`git add <file>`)합니다.
- **사용자의 최종 커밋 및 푸시 승인을 받은 후에만** `git commit` 및 `git push`를 실행합니다.

## 📋 검증 상태 관리 원칙

학습 포트폴리오의 신뢰성을 위해 다음 상태 모델을 준수합니다:

| 영역 | 점검 항목 | 기록 원칙 |
| :--- | :--- | :--- |
| **A. 학습 기록** | 개념 학습 / 코드 분석 / 직접 구현 / 복습 및 이해도 확인 | 실제로 수행한 학습 단계만 기록 |
| **B. 기술 검증** | 구문 검사 / 빌드 / 실행 / 시뮬레이션 / 실기기 검증 | 객관적 실행 결과가 확인된 항목만 기록 |
| **C. 확인 필요 사항** | 미검증 항목 / 검증 불가 사유 / 재검증 필요 조건 / 출처 | 한계와 의존성을 투명하게 명시 |

> [!CAUTION]
> 코드가 정상 빌드되고 콘솔 출력이 나왔다고 해서 학습자의 개념 이해가 완료된 것은 아닙니다. 기술 검증(실행 확인)과 학습 기록(원리 이해)은 항상 분리하여 정직하게 기록합니다.
